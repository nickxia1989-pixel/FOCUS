# 多端同步（坚果云 WebDAV）的实现

调研和路线选择见 [sync-research.md](sync-research.md)。这里记录实际实现、冲突规则和测试方法。

## 总体

```
 桌面（Electron）                         iPhone（Capacitor）
 store.ts ── src/sync/ops.ts ──┐   ┌── src/mobile/store.ts
 syncDesktop.ts（主进程转发请求） │   │   src/mobile/sync.ts（CapacitorHttp，原生 URLSession）
                               ▼   ▼
                     src/sync/（两端共用的纯 TS）
                     clock · doc · file · migrate · engine · webdav
                               │
                坚果云 WebDAV：<同步文件夹>/devices/<deviceId>.json
```

- 两端都直连 WebDAV。桌面的请求由 Electron 主进程发出（渲染进程拿不到密码，也没有跨域问题）；iOS 用 `CapacitorHttp`，走原生网络，不受网页跨域限制。
- **每台设备只写自己的文件** `devices/<deviceId>.json`，内容是这台设备合并后的完整文档。同一个文件只有一个写入方，网盘不会产生冲突副本；读别人的文件、合并进自己的文档。
- 本机始终是第一数据源：离线照常用，联网后补传补拉。

## 数据模型（`src/sync/doc.ts`）

每条待办拆成几个寄存器，各自合并：

| 寄存器 | 字段 |
| --- | --- |
| `title` | 标题（冲突时附带候选值 `alts`） |
| `status` | 完成、完成时间、完成时所在列表、待测 |
| `pos` | 父项、所在列表（子项的列表是派生值，跟随根项） |
| `order` | 手动排序（拖拽只改被拖那一项，取两邻居中点） |
| `del` | 删除时间（软删除 = 进回收站）、彻底删除（墓碑） |

profile 有 `meta`（名字、iOS 头像颜色）和 `del` 两个寄存器。折叠状态、界面偏好、当前 profile、窗口位置、凭证都只存本机。

每个寄存器带一个戳：
- **HLC**（混合逻辑时钟，`墙钟.计数.设备id`）：并发时决定谁算"后改的"，不依赖各设备时钟准确。
- **版本向量**：写入时这台设备已经知道的全部改动。用它判断两次改动是"一方看过另一方"（直接取新的），还是"真正并发"（需要合并规则）。

合并逐寄存器进行，满足交换律、结合律、幂等：不管以什么顺序、重复读多少次，所有设备最终一致。合并后按 id 排序做确定性清洗（孤儿提升、断环、子项跟随根项的列表），不产生新戳。

### 自动合并的规则

- 两边改的不是同一个寄存器：都保留（例如一边改标题、一边勾完成）。
- 同一个寄存器并发改动：**直接改动**优先于**连带改动**（完成父项时子项被连带完成、回收站过期自动清理），其次按 HLC 取后改的。
- 回收站过期自动清理和用户的「恢复」并发时，恢复赢。

### 需要旅行者决定的冲突

冲突完全由文档数据派生，所以每台设备看到的一致；在任何一台上做了决定（写入一个覆盖所有并发改动的新戳），其它设备同步后冲突自动消失。

1. **标题被并发改成不同内容**：所有候选值连同各自的版本向量留在 `title.alts` 里；被后来的改动因果覆盖的候选会被剔除。选项：用某一个 / 都保留（其余候选各复制成一条新待办）。两台设备同时做了不同决定时按时间取一个，不再反复弹出。
2. **删除 vs 修改**：一条被删除（或彻底删除）时，它自己或没被单独删除的子孙上有与这次删除并发的直接改动（含在它下面新加子项）。临时状态是"已删除"（在回收站里，内容都在）。选项：恢复 / 保持删除。
3. **删除整个 profile vs 在里面改**：冲突解决前这个 profile 仍然显示。选项：恢复 / 确认删除。

另外，编辑标题时记下开始编辑时的知识：编辑期间远端改了同一条标题，提交时会变成冲突，而不是用编辑框里的旧底稿悄悄盖掉远端的改动。

发现新冲突时自动弹出冲突面板（桌面：标题栏下的面板；iOS：底部面板）；没处理完的冲突在云朵图标上显示角标。

## 同步引擎（`src/sync/engine.ts`）

一轮同步：

1. `PROPFIND`（Depth 1）列出 `devices/`；文件夹不存在就逐级 `MKCOL`（根目录建不了时提示改用 `我的坚果云/FOCUS`）。
2. 对比各设备文件的修改时间和大小，只 `GET` 变了的（每 5 分钟无条件全读一次兜底）；文件头带 `seq`，读到比读过的还旧的内容（缓存）就跳过，下轮再读；读到半截或坏掉的 JSON 也跳过，绝不当成"对方没有数据"。
3. 合并进本机文档，刷新界面、写盘。
4. 上传自己的文件：本机有新操作（写入计数涨了）就立刻传；只是并入了别人的改动时不急，最多攒 10 分钟顺带上传，省请求次数。两次上传至少隔 1.1 秒（坚果云修改时间只精确到秒）。上传后核对服务器上自己文件的大小，不对就重传。

其它：
- 触发：本地改动防抖 2 秒；在线每 15 秒轮询；窗口获得焦点、App 回到前台、网络恢复、电脑唤醒时立即同步；退出、睡眠、锁屏、切到后台前先传完（iOS 用 `beginBackgroundTask` 申请后台时间，后台不轮询）。
- 出错：断网和服务器临时 5xx 按 15 / 30 / 60 秒重试；`503` 限流按 1 / 5 / 30 分钟退避；账号密码错误等更久。
- 身份：设备 id 存在系统钥匙串（iOS 是 `ThisDeviceOnly`，桌面用 `safeStorage` 加密）。数据目录被拷到别的电脑、从备份恢复到新手机时会生成新的设备 id；云端自己的文件里出现别的安装的 `nonce` 时，也会先并入它的数据再换 id。
- 第一次加入已有数据的云端：「合并本机数据」或「以云端为准」。选以云端为准时先备份本机文档，等第一次读到云端数据时整个替换（期间不会把本机旧数据传上去）。本机只有上手示例时直接以云端为准。

## 迁移

- 桌面：第一次启动新版本时把 `profiles.json` / `focus-data.json` / `profiles/*.json`（含回收站）迁移进 `focus-doc.json`，旧文件保留。
- iOS：把原来存在 Preferences 里的整份快照迁移进文件存储的文档。
- 迁移只走一次时钟，所有寄存器共用一个戳。

## 测试

### 单元测试（`npm test`）

- `src/sync/doc.test.ts`：时钟、各类自动合并、三类冲突的检测 / 决定 / 跨设备消失、三台设备不同到达顺序下候选值的剔除、编辑期间远端修改、连带改动与直接改动、过期清理与恢复、回收站软删除、设备文件校验、迁移。
- `src/sync/converge.test.ts`：随机收敛测试。3～5 台模拟设备、各自时钟有偏差，随机增删改移、标待测、拖拽排序、回收站、profile 改名和删除、随机决定冲突；随机离线、只上传或只下载、读到半截文件。最后全部互相同步，断言：各设备文档逐字节一致、没有丢任何记录、没有"已完成又待测"、子项跟随根项的列表、冲突在一台设备上全部决定后所有设备都没有冲突。共 180 组随机种子。
- `src/sync/engine.test.ts`：用内存里的假坚果云（修改时间精确到秒、父目录不存在回 409）测引擎：自动建文件夹、断网与补传、限流、只并入别人改动时不回传、读到旧文件、上传其实成功但回报失败、服务器上的自己文件不对时重传、别的安装冒用设备 id、忽略网盘冲突副本等杂文件。

### 本机联调

```bash
npm run dev:webdav     # 本机测试服务器 http://127.0.0.1:8765/dav/，账号 focus-dev / focus-dev-pass
```

管理接口可以模拟各种网络状况：

```bash
curl -X POST -d '{"offline":true}' http://127.0.0.1:8765/__admin/state          # 所有请求直接断开
curl -X POST -d '{"blockDevices":["<deviceId>"]}' http://127.0.0.1:8765/__admin/state  # 只断某台设备
curl -X POST -d '{"rateLimited":true}' http://127.0.0.1:8765/__admin/state      # 模拟坚果云限流 503
curl -X POST -d '{"failRate":0.5,"latencyMs":800}' http://127.0.0.1:8765/__admin/state  # 慢网 + 一半请求失败
curl http://127.0.0.1:8765/__admin/log                                          # 请求记录（数请求次数）
```

- 桌面：用不同的 `FOCUS_USER_DATA` 开两个实例当两台电脑；同步设置里的「模拟离线」开关可以让一台单独断网。
- iOS：`VITE_FOCUS_E2E=1 npm run ios:build` 构建测试包，App 会从测试服务器的命令队列（`/__e2e/*`）取命令，经过真实的 store、原生 HTTP 和钥匙串执行，方便脚本化地跑离线 / 冲突场景。正式构建（不带这个变量）里没有这段代码。

2026-10-17 用两个桌面实例 + iPhone 17 Pro 模拟器实测过的场景：两边离线各改很多后联网（不同条目自动合并、同一条标题冲突、删除 vs 修改）并在桌面和手机上分别决定；删整个 profile vs 在里面加事；坚果云限流；App 在离线改动后被杀掉再打开；改完立刻切后台；后台不轮询、回前台立即同步；一半请求失败的慢网下三台设备同时修改后最终一致。

同日在真实坚果云上用桌面版 + iPhone Duo 模拟器复测：两端在线互传（15 秒内到达）；两边离线分别改同一条标题、一边删除一边改标题，联网后两端自动弹出同样的两个冲突，在手机上选标题、在桌面上点恢复，几秒内两端冲突都清零、条目一致。

## 已知限制

- iPhone 在后台基本不同步（iOS 不允许常驻），打开或回到前台时立即同步。
- 墓碑和彻底删除的条目目前一直保留在文档里（内容也保留，方便"彻底删除 vs 修改"时恢复）；完成的历史也不会自动清理。数据量大了以后可以再做压缩或归档。
- profile 的名字和 iOS 头像颜色在同一个寄存器里，两边同时分别改名和改颜色时只保留一个。
- 模拟器里的 iPhone Duo 合上（外屏）姿态下自动化点击不生效，同步联调用的是 iPhone 17 Pro 模拟器。
